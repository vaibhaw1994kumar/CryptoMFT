# Economic event ledger and reconciliation

The economics work so far: an asset-level economic ledger, fee and rebate
accounting (ECO01), perpetual funding settlement (ECO02) and a closing-equity
reconciliation (ECO06 gate). Borrowing (ECO03), margin tiers and liquidation
(ECO04), transfers (ECO05), queue calibration and the CI build are later
milestones.

## Model (`src/crypto_stat_arb/economics.py`)

Every value-changing event is an `EconomicEvent` made of postings
`(venue, account, asset, quantity)`. Balances are therefore kept per venue,
account and asset: Binance USDT, Bybit USDT, Binance BTC and Bybit BTC never
pool. All amounts are `Decimal`.

| Event type | Generated by | Postings |
|---|---|---|
| `OPENING_BALANCE` | session start (config: `initial_capital_by_venue`, `risk.inventory`) | opening quote and base per venue |
| `TRADE_FILL` | every fill delta (and notional-only adjustment) in `Ledger.apply_fill`; effective at the venue match time | base (spot) or contract (perp) ±quantity, quote ∓notional |
| `FEE` | every fee delta | fee asset −quantity (cost) or +quantity (rebate) |
| `DEPOSIT` / `WITHDRAWAL` | operator / venue (API available) | external flows |
| `VALUATION_ADJUSTMENT` | operator | explicit adjustments |
| `REVERSAL` | `EconomicLedger.reverse` | exact negation of the original |
| `FUNDING` | `FundingEngine` at each settlement of a configured perpetual (ECO02) | settlement asset ±amount |
| `BORROW_ACCRUAL`, `BORROW_REPAY`, `TRANSFER` | **not generated yet** | reported `NOT_MODELLED` |

Each event carries an event id, idempotency key, event and effective
timestamps, venue/account/instrument, source (`SIMULATED`, `OBSERVED`,
`CONFIGURED`, `ASSUMED`), order/fill/reference ids, the reporting-currency
value at the time of the event, the valuation price and its provenance.

* **Idempotency.** Keys derive from cumulative source values (order id +
  cumulative quantity/notional/fee), so a replayed or restarted event maps to
  the same key. Same key + same payload: ignored and counted. Same key +
  different payload: `ConflictingEventError`.
* **Corrections** are `REVERSAL` events that must negate the original's
  postings exactly; history is never rewritten and an event can be reversed
  once.
* **Ordering.** An event effective before one already booked is accepted and
  flagged as late; `balance(..., as_of_ns=t)` replays events by
  `(effective_ts, ordinal)`, so any historical state can be reconstructed.
* **One source of truth.** The economic ledger lives inside `Ledger`
  (`ledger.economics`) and is rebuilt with it on restart. The trade
  bookkeeping (positions, cash, realized/unrealized PnL) is unchanged; risk's
  `held_base` / `held_quote` read asset balances once opening balances are
  booked, so base paid away in fees cannot be sold.

## Fees and rebates (ECO01)

Fee rules (`fees` in config) accept (comments for illustration only):

```jsonc
{"venue": "BINANCE", "instrument_id": "BTC-USDT-SPOT",
 "maker_fee_bps": "-1", "taker_fee_bps": "4",
 "fee_asset": "QUOTE",            // QUOTE (default) | BASE | token symbol, e.g. BNB
 "fee_source": "VERIFIED",        // VERIFIED (account tier confirmed) | ASSUMED (default)
 "conservative_unverified": true, // ASSUMED maker rebates are booked at 0 bps
 "effective_from": "2026-10-01T00:00:00Z", "tier": "VIP0"}
```

* **Per-fill pricing.** Each fill delta is priced at the liquidity of that
  fill: the execution adapter labels fills `TAKER` (matched on arrival) or
  `MAKER` (a resting order filled later); `post_only` is the fallback. A GTC
  order filled partly on arrival and partly later is `MIXED` and charged per
  fill.
* **Recorded per order:** `fee` (reporting-currency value: cost positive,
  rebate negative), `fee_asset`, `fee_quantity`, `fee_rate_bps`,
  `liquidity`, `fee_source`.
* **Assets.** QUOTE fees reduce quote cash. BASE fees reduce base, not cash.
  A third-token fee needs a price in `OMS.asset_prices`; without one the fee
  is booked with its value but no quantity, flagged `FEE_ASSET_UNPRICED`, and
  the reconciliation reports `INCOMPLETE` (never silently charged in quote).
* **Rebates** are credits. The fee-regression guard compares magnitudes, so
  a rebate growing more negative across partial fills is accepted, and a
  venue-reported fee replaces the computed one only if larger in magnitude.
* Entries, exits, hedges and unwinds are all fills, so all pay fees.

## Funding settlement (ECO02, `src/crypto_stat_arb/funding.py`)

Applies to instruments with `product_type` `PERP`/`PERPETUAL`/`LINEAR_PERP`/`SWAP`.
On spot, funding is reported `N/A`.

```jsonc
// instruments[]: contract terms
{"instrument_id": "BTC-USDT-PERP", "product_type": "PERP",
 "contract_type": "LINEAR",          // INVERSE is rejected at load (not supported yet)
 "contract_multiplier": "1",         // values other than 1 are rejected at load
 "settlement_asset": "USDT",         // default: quote
 "funding_interval_hours": 8,        // or funding_interval_minutes; required (missing data is detected against it)
 "funding_anchor": "1970-01-01T00:00:00Z"}
// top level: rate records and rules
"funding": {
  "rates_path": "data/funding/binance_bybit.jsonl",   // and/or inline "rates": [...]
  "settle_lag_ms": 5000,        // wait for late fill reports before settling
  "max_rate_age_ms": 60000,     // a record observed earlier than this is stale; unset = stale detection off
  "mark_fallback": "none"       // or "book_mid" (labelled an approximation)
}
// a rate record (one JSON object per line)
{"venue": "BINANCE", "instrument_id": "BTC-USDT-PERP", "funding_ts_ms": 1760947200000,
 "rate": "0.0001", "mark_price": "60000", "source": "OBSERVED", "asof_ts_ms": 1760947200000,
 "predicted": false}
```

* **Amount.** Linear: `-contracts × multiplier × mark × rate` in the
  settlement asset. Inverse: `-contracts × multiplier / mark × rate` in base.
  Longs pay a positive rate and shorts receive it.
* **Event.** One `FUNDING` event per settlement, with key
  `funding|venue|instrument|ts|r<revision>` and effective time equal to the
  settlement time. It carries rate, mark, position, multiplier, interval,
  revision and the record's source (`OBSERVED` from venue history,
  `SIMULATED` from a scenario file). The legacy trade ledger books the same
  cash, so `account_state.json` has a `funding` column and its equity
  includes funding.
* **Position at settlement.** This is the as-of contract balance by **venue
  match time**: `TRADE_FILL.effective_ts_ns` is the venue time at which the
  cumulative fill was first reached, not when the report arrived. Taker
  fills are stamped at order arrival and resting maker fills at the book
  update that crossed them, in both the report and the queryable order
  status.
  Boundary: a fill matched strictly *before* the settlement timestamp counts;
  one matched *at* it does not.
* **Late fills.** If a fill matched before a booked settlement is reported
  afterwards, the settlement is reversed (`REVERSAL`) and rebooked as the
  next revision, and `LATE_FILL_REBOOKED` is flagged. `settle_lag_ms` keeps
  this rare.
* **Data.** Settlement times are the union of the rate records and the
  configured schedule. A settlement with a position and no record
  (`FUNDING_RATE_MISSING`), a stale record (`FUNDING_RATE_STALE`) or no mark
  (`FUNDING_MARK_MISSING`) books nothing and makes the reconciliation
  `INCOMPLETE`. The same flags while flat are informational. Duplicate
  identical records are ignored; conflicting ones raise.
* **No double settlement.** Each settlement is processed once per revision,
  and re-running settlement on the same ledger is ignored by the idempotency
  key. A perpetual without a funding interval is rejected at load (and
  reported `FUNDING_SCHEDULE_UNKNOWN` if built directly), because a missing
  record could not otherwise be detected.
* **Horizon.** Settlement is booked only up to the last market event, never
  past the data (even when the drain horizon is longer).
* **Predicted funding** (records with `predicted: true`, i.e. the venue's
  current or next rate) is reported in `funding_report.json` → `predicted`
  and is never booked.
* **Artifacts.** `funding_report.json` holds status, settlements, flags,
  realized by venue, predictions and rules. `economic_reconciliation.json`
  has a `funding` row per venue and a `<venue>_funding_matches_trade_ledger`
  check. `plan_net_pnl_matches_equity_pnl` compares plans with equity PnL
  *excluding* funding and borrow, since plans hold trading economics only.

## Reconciliation (`economic_reconciliation.json`)

Written by every backtest and paper run, summarised in `summary.json`
under `economics`. Per venue and consolidated, in the reporting currency
(USDT):

```
closing equity = opening equity
               + inventory revaluation   (opening balances × price change)
               + trading PnL             (trade postings at closing marks)
               + fees and rebates        (fee postings at closing marks)
               + funding                (perpetuals; N/A on spot)
               − borrow + transfers      (NOT_MODELLED for now)
               + deposits + withdrawals  (external flows, not strategy PnL)
               + valuation adjustments
```

Fees are also reported at fill-time value with the fee-asset revaluation
separate. `strategy_equity_pnl` excludes inventory revaluation and external
flows, so pre-funded inventory drifting in price is not presented as
strategy profit.

The identity holds by construction; the **gating checks** compare it with
independent computations:

| Check | Comparison |
|---|---|
| `<venue>_identity_exact` | closing equity − explained = 0 exactly |
| `<venue>_trading_pnl_matches_trade_ledger` | trade postings at closing marks = trade ledger realized + unrealized PnL (within 1e-9: the trade ledger's average-cost division rounds in the 28th digit) |
| `<venue>_fees_match_trade_ledger` | net fees = trade ledger fees (exact) |
| `<venue>_funding_matches_trade_ledger` | economic funding = `account_state` funding (perpetual venues) |
| `plan_net_pnl_matches_equity_pnl` | sum of plan net PnL vs strategy equity PnL excluding funding/borrow (tolerance 1 USDT: plans mark residuals at close-time mids) |
| `<venue>_matches_venue_reported_equity` | when venue equity is supplied (`NOT_AVAILABLE` in simulation/internal paper) |

Status: `RECONCILED` (all checks pass), `INCOMPLETE` (a price/FX is missing,
a fee asset is unpriced or funding data is missing/stale for a held position;
nothing is assumed), `FAIL` (a check failed).

## Not yet covered

* Funding is implemented and unit-tested (`tests/test_funding.py`), with an
  end-to-end perpetual backtest on relabelled sample data. **It has not been
  run on recorded perpetual data**: every recorded cycle is spot, where
  funding is `N/A`. A public funding-history fetcher is not included yet.
* Funding is not yet persisted or rebuilt on an OMS restart:
  `rebuild_from_plans` replays fills only.
* Stale-rate detection is off unless `max_rate_age_ms` is set.
* Perpetuals: inverse contracts and multipliers other than 1 are rejected at
  load. Margin is not modelled (ECO04): contract positions are valued at
  mid × multiplier, an approximation of the mark price.
* Borrow lifecycle and transfers: event types exist with no generator;
  reported `NOT_MODELLED`, never zero.
* Account-specific fee tiers are only as good as the configured
  `fee_source`; unverified tiers are labelled `ASSUMED` on every fee event.
* Quote reservations in risk admission do not yet include fees.
* The maker dry-run simulator's fills are a separate harness and are not
  booked in this ledger.
* Venue-reported balances/equity are not available in simulation or
  internal paper mode.
