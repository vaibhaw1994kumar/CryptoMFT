B0.3 Bid or ask rounded onto the touch: new switch

Rule (switch arb.join_touch_on_tick_rounding, default off). If the quote was inside the spread before tick rounding and lands exactly on the best price once rounded, it joins the back of that level's queue (the full displayed size is ahead of it) provided the edge at the rounded price passes the same gate; otherwise it is refused as before. A quote that rounds below the touch is still refused. Both sides use the rule (I built the ask side as the mirror; only the bid side is exercised in the runs). The edge check cannot actually fail after rounding: rounding a bid down (an ask up) only improves the edge, so the "refuse if the edge no longer passes" branch exists but is unreachable in practice; it is counted separately (tick_rounding_join_no_edge) so you can see if that ever changes. Queue position was checked in the engine: an order placed on a visible level gets queue ahead = the displayed size (03-09 example below: 221.6), not a fitted draw.

What the scenarios found

  • Scenario 5 is the open ghost defect, now pinned, with both halves of Demonstration 1. With a gateway outage the backtester writes the hedge off after 2 s, unwinds the maker fill, and the original hedge then lands at reconnect: the account ends short 1.2 that nobody asked for. The requirement (OMS03, Demonstration 1) says query before replacing and never understate the reserve. The reserve half works today only with the profile's mandatory switches (count_pending_exposure, count_unknown_exposure): on, the 1.2 binance sells are held from 6.0 s until the ghost lands; off (the legacy setting) the reserve is empty while 1.2 is live. The replacement half fails. Phase E must turn the target test green and update the today tests.
  • Scenario 13: the maker engine's answer depends on the order of two events. With two of our orders at one level, MakerExecutor gives a different result depending on whether the print or the matching depth update arrives first (print first: the second order gets nothing; depth first: both fill). I checked it under two configurations: the parity test's (trades only, all_ahead) and the maker block of perp_perp_maker_taker_v1_1 (proportional, trade_confirm, print-against-depth netting): same two answers in both. The core queue engine is order-independent and uses one budget. The under-fill half is the already-pinned difference D2; what is new is that it also depends on event order. It cannot occur in v1.1 runs (maker_max_live_orders is 1 in every profile, so two own orders never share a level); it becomes reachable when more than one live order is allowed, which is a Phase D/E question.
  • Scenario 3b confirms C9 with a concrete case. In the legacy setting (fill_evidence: off), the level we rest on going 3 to 0 to 2 to 0 with no print at all fills 0.3 and the hedge follows. The v1.1 setting does not. My first draft of this scenario passed in both modes and proved nothing; the depth-only sequence above is the one that shows it.
  • Scenario 11: the liquidation fill pays the venue taker fee and the liquidation fee. That is by design in the backtester (a code comment says so). My hand calculation assumed the liquidation fee replaces the taker fee, so it was wrong by 0.088. Whether a real venue charges both is a Phase B question (matrix A10).
  • Scenario 15 is partly covered already. The brief said this window has no test. A close one exists (test_restart_resilience.py: an adapter raises after the intent is durable), but it raises an ordinary exception, so the OMS writes an "ambiguous dispatch" record. My scenario raises a kill the OMS cannot catch, so nothing is recorded. I expected a gap here and there is none. What cannot be tested yet is the last step: a replacement after the venue says "unknown", which needs the Phase C deferred send path.
