D2 Queue-Floor Audit Report

Full investigation of whether min_queue_ahead is active, how absent-level placements flow through to fills, and whether the reported fill rates are inflated.

Executive Conclusion — D2 is inactive in the sol_2022_backtest run. min_queue_ahead = 0.0 in every code path that reaches the backtester; no CLI flag, config file, or override sets it to a non-zero value. As a result, 89.2% of maker placements start with zero initial queue, and the reported 1-second fill rate of 82.8% is the rate for a zero-queue simulator, not for an order joining a real FIFO queue. The fill rate for the 10.8% of orders that did observe a non-zero level was 75.0% — 8.8 percentage points lower. The magnitude of inflation from D2 alone cannot be precisely quantified without a controlled re-run, but the direction is confirmed: current rates are optimistic for instruments where the quoted level is typically present.

2. Code-Path Trace — Absent-Level → Zero Queue → Instant Fill

Following the full path from strategy signal to fill for an absent-level order:

1. strategy.evaluate() fires ArbSignal (mode=MAKER_TAKER, maker leg)
2. _fire() → _send_leg() → pending.enqueue(release_ts = now + entry_latency)
3. Event loop: pending.release(now) → _execute_arrival(order, now)
4. _execute_arrival():
     if not book.ready: miss → return                    # guarded by caller ✓
     maker_order = self.maker.place(
         price=order.limit_price,
         book=book, active_ts=now,                       # placed_ts = active_ts = now
         tick_size=self.tick_size[venue],
     )

5. place() → _level_size(book, side, price, tick_size):
     tol = max(1e-12, 0.5 * tick_size)                  # e.g. 0.005 USDT for SOL
     for lv_price, lv_size in book.levels(side, 50):
         if abs(lv_price - price) <= tol: return lv_size
     return 0.0                                           # ← level absent

6. level_size = 0.0
   initial_q = 0.0 * 1.0 = 0.0                          # queue_stress_multiplier=1
   # D2 check:
   if level_size == 0.0 and config.min_queue_ahead > 0.0:  # ← False (0.0 > 0.0 is False)
       initial_q = config.min_queue_ahead                # ← NEVER REACHED
   order.queue_ahead = 0.0
   order.observed_level_size = 0.0

7. On next DELTA or TRADE event at order.price:
   _consume(order, volume=V, fill_share=delta_fill_share=0.15):
     available = V
     # queue drain:
     drained = min(0.0, V) = 0.0                        # queue=0 → nothing to drain
     available = V - 0 = V                               # full volume available
     qty = min(order.remaining, V * 0.15)               # immediate partial fill
     → Fill emitted

The zero-queue order receives its first fill attribution on the very first delta event that touches its price level, with no queue to consume first. For a level with only 1 SOL resting (order size 0.5 SOL), a delta shrink of even 0.1 SOL produces a fill of min(0.5, 0.1 × 0.15) = 0.015 SOL. Because delta events are frequent on liquid instruments, many small fill attributions accumulate quickly into a full fill. This is why observation_time_s ≈ 0 for filled zero-queue orders and fill rates at 1s are high.

CONFIRMED BY CODE Absent-level orders always start with queue_ahead = 0.0 and receive fill attribution on the first touching delta event.

4. D3 / D4 Audit

D3 — Trade tape + delta double-count

D3 occurs when the same economic volume appears in both a TRADE event and a DELTA event, causing _consume() to be called twice for the same volume. Expected overcount factor: 1 + delta_fill_share = 1.15.

Measured impact: Only 1 out of 443 H=1 fill records (0.2%) had both trade_fill_qty > 0 AND book_event_fill_qty > 0. The combined qty for that one record was 1.0 SOL (order size). D3 is measurable in this dataset and its impact is negligible for the Jan 2022 SOL data.

CONFIRMED BY DATA D3 contributed to at most 0.2% of fills. Not a material source of fill rate inflation for this dataset.

Note: the low D3 rate likely reflects the exchange's event stream: Bybit and Binance send TRADE and DELTA as separate events only rarely overlapping for the same level shrink in the same event batch. The 1.15× theoretical factor applies only to the minority of events where both fire.

D4 — Cancel vs. trade attribution in delta events

D4: when a bid/ask level shrinks, on_delta() calls _consume() with delta_fill_share=0.15. The shrink could be a cancellation (no actual trade at our price) or a real trade. On L2 feeds we cannot distinguish them.

Looking at zero-queue fill attribution: 179.2 SOL filled by delta events vs. 211.6 by trade events. Delta events are responsible for ~46% of zero-queue fill volume. The fraction of those deltas that represent genuine trades (vs. cancels) is not measurable from L2 data alone.

NOT MEASURABLE with available L2 data. Would require a trade tape matched against the delta stream with unique event IDs.

What is defensible: the delta_fill_share=0.15 constant means the simulator assumes 15% of any level shrink reaches our order. Whether this calibration is correct is an open empirical question.

Phase 3 — Calibration Methodology

A defensible calibration for min_queue_ahead requires separating two questions: (1) what is the typical queue depth when our level IS present? (2) what is the appropriate floor for when it is ABSENT?

What to measure

From the 10.8% of placements where _level_size() > 0, extract the distribution of observed level sizes at placement. Segment by: quoting side, distance-from-touch ticks, spread bucket, book-depth bucket, time of day.

A conservative estimate: set min_queue_ahead to the 25th percentile of the present-level distribution for that (instrument, side, ticks-away) bin. This is neither best-case (0) nor worst-case (full visible depth).

Leakage guardrails

Calibrate min_queue_ahead from a separate calibration window that predates the evaluation window, the same way WalkForwardCalibrator handles fill probability models. Never calibrate on the same day you evaluate.

The empirical fill model learns from the simulator's own outputs. If min_queue_ahead=0 creates fast fills, the model learns "orders fill fast" and re-inforces optimistic gates. Fixing D2 must happen in Pass 1 to prevent this circular self-reinforcement.

Regression Test Plan

Absent-level / min_queue_ahead

  • Place order at level absent from book → queue_ahead = min_queue_ahead
  • Place at absent level, min_queue_ahead=0 → queue_ahead = 0
  • Place at present level, any min_queue_ahead → floor NOT applied
  • Place at present level, queue_stress=0 → queue_ahead=0, min_queue_ahead not applied

Queue drain correctness

  • Trade of V units at price → queue_ahead drains by min(V, queue)
  • Delta shrink → drain by delta_fill_share × volume after queue
  • Two orders at same price → queue drain is independent (not sequential)
  • Order placed after replenishment → observed_level_size does not increase

D3 / event deduplication

  • Trade then delta for same V → combined fill = V + V×0.15 (1.15× baseline)
  • Delta alone for V → fill = V × 0.15
  • Trade alone for V → fill = V × 1.0 (after queue drain)

Replay determinism

  • Same config, same seed → identical fill_events.jsonl
  • Changing min_queue_ahead → fill rates change monotonically
  • Cancel at end of run → records appear in fill_events.jsonl with terminal_reason=cancel
