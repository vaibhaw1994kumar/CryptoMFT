1. Executive summary

The maker (passive, post-only) simulation previously ran in a separate “universe” from the rest of the platform: its own flat 10 ms latency, wall-clock timing, raw-dictionary trades and a Python fallback model, while the C++ matching engine had never been compiled or exercised. This session unified it with the platform’s existing abstractions and verified the result end to end.

  • One execution path: canonical MarketEvent + new TradeEvent → one event clock (SimulationClock) → platform LatencyModel → venue arrival → C++ mm::MatchingEngine → print-driven fills → fill-report latency → strategy.
  • Queue position at venue arrival (decision + strategy + risk + entry latency), cancel races, post-only rejects, delayed inventory knowledge and preserved queue priority are now modelled.
  • C++ engine integrated and corrected (three queue-accounting bugs fixed), with a bit-identical Python mirror and parity tests.
  • Sensitivity: adding 35 ms of market-data staleness reduces filled quantity by 3.82% (Binance) / 3.92% (Bybit) and 75 ms by 7.88% / 8.23%, while the 1-second markout per fill moves by at most 0.014 bps. The results are not produced by stale-book optimism.
  • Economic finding: at-touch passive quoting loses ~1 bps per fill to adverse selection plus a 2 bps maker fee — negative in all 28 aggregated scenarios.

3. Improvements implemented

3.1 P0 – Core architecture

GapWhat was done
Latency parityMaker builds its latency from the config latency section (same preset/overrides as the OMS) as a separate instance with a derived seed, so OMS draws are unchanged. Stage composition mirrors the OMS: decision t → dispatch t+strategy+risk → arrival +entry; cancel applies +cancel; fill reports +fill; acks/rejects +submit_ack. maker_simulation.latency_ms now raises an error; maker_simulation.latency overrides individual stages (e.g. 300 ns entry).
Queue at arrivalOrders join the C++ queue at venue arrival against the book at that instant. Cancels apply after cancel latency and the order can still fill meanwhile. Post-only orders crossing at arrival are rejected. Strategy inventory changes only when the fill report is observed; the inventory band uses that view plus all unfinished orders.
Canonical tradesNew models.TradeEvent (sibling of MarketEvent, schema 1.1.0, reads legacy rows) and EventType.TRADE. canonical.py validates and dispatches both types with type-filtered sinks. Normalizers emit TradeEvent (TradeTick kept as alias). Live feed validates every trade envelope.
One event clockNew sim_clock.SimulationClock: schedule, advance_to, drain; deterministic (ts, sequence) order; timers due at an event fire before it; monotone time with regression counter. Live paper now uses each event’s receive_ts_ns.

3.2 P1 – Ordering, fills, cadence

GapWhat was done
Native orderingLive feed stamps one arrival_ordinal across book and trade streams (written to trace.jsonl and TradeEvent). Replay reproduces the live interleaving from the trace (older traces: line order). Fallback key: receive time → exchange time → declared per-venue kind priority (replay_tie_priority) → event id. Native book/trade sequences are never compared. Duplicate ids fail closed to the fallback.
Print-driven fillsmaker_engine.py: CppQueueEngine wraps the compiled engine with an explicit id map; PythonQueueEngine mirrors the arithmetic exactly. Every fill row records the causing trade_event_id, queue ahead at arrival and decision/dispatch/arrival/match/report timestamps. Book crossings without a print are counted (crossed_without_print), never filled.
Cadence vs latencyquote_interval_ms is a clock timer (strategy scheduling). Unchanged quotes keep resting and keep queue priority; moved quotes are cancelled and replaced.

3.3 C++ matching engine (sim_engine/include/mm/matching_engine.hpp)

  • Compiled for arm64 / Python 3.12 (pybind11 3.1.0) into sim_engine/; now the default (engine="auto" → cpp_mm_matching_engine).
  • Level sizes come only from the book feed; trades only burn queue ahead.
  • Several own orders at one level share a print: only our own fills absorb volume.
  • Book updates can only cap queue ahead; the capped amount is a clamp_credit so a print and its book delta count once in either arrival order.
  • Print strictly through our price → full fill at our price. Size-0 level keeps our resting orders.
  • New set_queue_position_frac (0–1, default 1.0 = back of visible queue).

3.4 Calibration and analysis features

  • queue_position_frac – share of the visible level ahead of a new order (old Python model hard-coded 0.7).
  • feed_lag_ms – market-data staleness; venue instants are placed later on the receive-time clock.
  • Per-fill markouts (markout_horizons_ms, default 1 s, 5 s) as an adverse-selection measure.
  • scripts/maker_sensitivity.py – parallel sweep with CSV/JSON/Markdown output and --from-csv re-aggregation.
  • Report schema 2.0.0 adds quotes kept, post-only rejects, cancel races, queue ahead, order states, latency percentiles; replay rejects invalid envelopes with counts; session audit adds latency source and an arrival-order check.

6. Sensitivity study: market-data delay × queue position

Question: how much of the simulated maker outcome survives when we remove the assumption that the observed book equals the venue book at order arrival?

Method: 84 deterministic replays on the C++ engine, ordering arrival_ordinal, cycles 0006, 0007, 0008, 0009, 0010, 0040 (≈30 min of live Binance + Bybit data each, 14–15 Sep 2026). Swept feed_lag_ms ∈ {0, 5, 10, 20, 35, 50, 75} and queue_position_frac ∈ {1.0, 0.7}. Quantity fill rate = filled qty / (orders sent × 0.001 BTC). Markouts: signed mid move after each fill (positive = favourable). PnL is mark-to-market incl. fees and inventory drift.

Findings

FindingEvidence
Delay costs some fills, smoothly – no cliffFilled quantity -3.82% Binance / -3.92% Bybit at 35 ms; -7.88% / -8.23% at 75 ms (fill rate -3.84% / -4.55% and -8.55% / -9.16%; frac 1.0)
Per-fill economics unchanged → results not driven by stale-book optimism1 s markout −0.94 → −0.96 bps (Binance), −1.01 → −1.01 (Bybit) from 0 to 75 ms
Queue position matters little for at-touch quotesfrac 0.7 vs 1.0 changes filled qty ~1%; 38% (Binance) and 57% (Bybit) of fills are trade-throughs
Post-only rejects are the strongest delay signatureBinance 157 → 388, Bybit 55 → 409 from 0 to 75 ms — best calibration target vs real testnet reject rate
At-touch passive harness is negative in every scenario≈ −1 bps adverse selection per fill + 2 bps maker fee; fees ≈ 58% of the loss
Proposed acceptance criterion (September data, cycles 0006–0010 and 0040; to be repeated across other regimes before it becomes a platform-wide invariant): at 35 ms market-data delay, filled quantity falls by ≤ 5% and the 1-second markout per fill shifts by ≤ 0.1 bps. 7. Known limitations

  • Queue calibration (P2) not done – needs real order outcomes (testnet post-only orders).
  • Default feed_lag_ms = 0 keeps OMS parity; the sweep quantifies the bias rather than removing it.
  • Book envelope does not carry arrival_ordinal (its JSON schema rejects extra fields); replay joins it from trace.jsonl.
  • Maker report schema 2.0.0: “quotes” = orders sent; old and new cycle totals in AUDIT_REPORT.md are not comparable.
  • Compiled module is arm64 / Python 3.12 and git-ignored; Docker/CI fall back to the Python mirror until a build step is added.
  • FAST_MM’s own copy of the C++ engine still has the queue bugs; vendored dry_run_core.py/sim_fill_engine.py are now unused.
  • Sweep covers one market regime (14–15 Sep 2026); PnL includes inventory drift.
